# 扑克画面识别改进记录

## 2026-08-04：不影响牌框的前提下识别底部操作区

### 状态

已修复，并完成回归测试。

### 现象

腾讯会议实盘中，终端反复打印 `hero_action_controls_not_visible`，但扑克
窗口底部明明显示了操作按钮。于是程序无法确认是否轮到我方玩家操作。

### 根因

这不是外框被改错，也不是最初手动框选不准确。最初的大框仍正确保存在
`analysis_bbox.json` 的 `outer_region` 中。

问题在于旧实时流程把复核后的内部牌桌框同时用于两件不同的事：

1. 识别手牌、公共牌、庄家、座位、底池和下注；
2. 截取整张图并寻找底部操作按钮。

内部牌桌框的下边界正好在操作按钮上方，因此按钮行在进入按钮识别前已经
被物理裁掉。程序拒绝仅凭筹码数值或滑条百分比猜测是否轮到我方，这个安全
规则本身没有错；错误是裁图让它报告了误导性的“未看到操作按钮”。

### 固定设计规则

一次校准必须保留两种区域：

1. **完整扑克窗口**：第一次拖出的较大框，必须含完整扑克客户端和最下方
   操作行。只用于检查弃牌、过牌、跟注、下注、加注和全下等按钮。
2. **内部牌桌**：复核时确认的青色框。用于稳定的手牌框、公共牌框、庄家
   定位、座位、底池和可见下注识别。

现在每帧先截取完整扑克窗口，再裁出内部牌桌进行牌面与牌桌识别；按钮识别
始终使用未裁掉的完整扑克窗口。未来任何修改都不得把这两个输入重新合并成
仅使用内部牌桌的一张图。

### 复现证据

来源截图：
`video_frames/screen_live/card_samples/sample_20260804_211624_0016_0213p513s/screen_context.png`

使用已保存的校准坐标得到：

| 输入图 | 结果 |
|---|---|
| 完整扑克窗口：`1214 x 854` | 检测到 1 个红色按钮；按钮文字识别到“快速弃牌”和“过牌”。 |
| 内部牌桌：`986 x 651` | 检测到 0 个红色按钮，也没有任何操作文字。 |

因此，旧问题由裁剪引起，不是牌面识别器错误，也不是外框选错。

### 实现与回归检查

- `gto_cli/bbox_utils.py` 从复核校准文件读取 `outer_region`。
- `gto_cli/cli.py` 分别将内部牌桌和完整扑克窗口传给实时截屏流程。
- `gto_cli/screen_vision.py` 用内部牌桌识别牌面，用完整扑克窗口识别操作区。
- 自动化测试覆盖“内部图中看不到、完整图中能看到”的按钮场景。
- 验证结果：`62 passed in 1.68s`。

### 对使用方式的影响

已有的复核后命令无需重做校准，直接运行：

```powershell
Invoke-Expression (Get-Content -Raw "video_frames\screen_calibrate\run_reviewed_overlay_command.txt")
```

当屏幕上确实没有正常的我方操作面板时，
`hero_action_controls_not_visible` 仍可能出现；修复后，它不应再仅仅因为
按钮位于内部牌桌框下方而出现。

## 2026-08-04 补充：自动定位时也必须保留第一次大框

在实际运行中，用户使用的是 `bbox.json + --auto-bbox`。其中 `bbox.json`
就是第一次手动拖出的完整扑克窗口；`--auto-bbox` 之后生成的是更紧的内部
牌桌框。此前完整窗口按钮识别只在复核文件包含 `outer_region` 时才启用，导致
这条常用命令仍会错误地把自动生成的内部牌桌用于操作按钮识别。

已修复为：无论使用 `bbox.json` 还是 `analysis_bbox.json`，操作区始终读取
第一次大框的完整扑克窗口；自动定位只能更新内部牌桌。样本截图中绿色框表示
完整扑克窗口（操作按钮输入），黄色框表示内部牌桌（手牌和公共牌输入）。

自动内部牌桌宽度至少要达到完整窗口的 68%，并覆盖到完整窗口高度的至少 88%，否则会切掉底部手牌。遇到
这种候选框，程序会保留第一次手动选择的完整窗口进行识别，并在后续刷新中继续
等待合格的内部牌桌框。

若自动定位一开始完全找不到牌桌，也不再终止实时流程；同样先使用第一次手动
选择的完整窗口。这样自动定位只是提高稳定性的辅助步骤，不会覆盖已知有效的
手动边界。

## 2026-08-17：第二批跨机器错误帧

### 结论

第二批并非全部与第一批相同。完整复现后分为四类：

1. 公共牌 `Qh`、`3h` 和手牌 `6d` 的数字或字母模型缺少当前缩放样本；
2. 方片花色在二值化时与紫色牌边粘连；
3. 三个红色操作按钮均存在，但文字识别偶尔漏掉最左侧“弃牌”；
4. 跟注额 `17.4BB` 偶尔被读成 `17.BB`，以及左侧 `1BB` 与玩家筹码区域重叠。

发牌动画帧和无法从单帧还原完整翻前行动历史的帧不是识别器错误，仍必须等待。

### 修复

- 把四张完整错误牌加入自动回归，并把人工确认的 `Q`、`3`、`6` 字形随仓库发布。
- 红色手牌花色改为先按颜色提取独立连通区域，避免牌边进入方片形状。
- 只有检测到三块水平对齐、大小近似的红色按钮，且已经读到“跟注”和“加注”时，
  才补回漏字的“弃牌”。两个按钮的“过牌/下注”面板绝不会自动增加弃牌。
- 只有加注额存在、且其一半与 `17.BB` 的整数部分一致时，才恢复被吞掉的小数。
- 只有原始文字本来就是不大于 `2BB`、且紧贴固定下注锚点时，才允许无筹码图标的
  盲注穿过玩家筹码区域。`81BB` 先被修成 `1BB` 的情况不会被放行。

### 回归证据

- 第一批独立压缩包：`10/10` 通过，两个证据不足场景仍保持等待。
- 第二批关键牌：`Qh`、`3h`、`6d`、`Qd` 全部正确。
- 第二批按钮重放：事件 374、403、815、1007、1055、1072 均恢复完整三按钮；
  事件 790 的跟注额恢复为 `17.4BB`。
- 第二批下注重放：事件 374 与 828/831/832 的左侧 `1BB` 恢复；事件 329 仍只确认
  `3.4BB / 8.2BB`，因此继续等待。
- 之前人工确认的字形集合：公共牌旧模型与新模型均为 `206/206`；手牌旧模型与新模型
  均为 `449/450`，没有新增错误或预测变化。
